# 1・3・4・7の事業構成と引き継ぎ方針

2026-10-31時点で `outreach` / `office-worker` / `content-engine` の既存コードを確認した判断です。動画制作・動画編集のリポジトリは今回の調査・変更対象に含めません。

## リポジトリの役割と名前

| 事業 | リポジトリ | 役割 | お金になる対象 |
| --- | --- | --- | --- |
| 1. 業務自動化の受託・テンプレ再販 | [office-worker](https://github.com/nyu1791-collab/office-worker) | 顧客のCSV・Excel・請求書を処理し、案件用ツールを作る | 初期制作費・追加改修・保守・匿名化済みテンプレ |
| 3. 個別営業 | [outreach](https://github.com/nyu1791-collab/outreach) | 営業先調査、提案文作成、フォーム入力、メール下書き | 自社受託の獲得・営業支援の構築費 |
| 4. SEO記事 | [content-engine](https://github.com/nyu1791-collab/content-engine) | CSVから記事を作る | 相談への誘導・契約済み紹介リンク・広告 |
| 7. 海外トレンドSNS | 同じ `content-engine` | 情報収集、記事・SNS文面生成、配信先別管理 | 記事への流入・相談・スポンサー |

名前は既存の3つを継続します。`lead-outreach` への改名や `solo-biz-suite` の新設は不要です。名前より先に動く商品と実績を作ります。

## 合併する範囲

4と7はすでに共通の収集・生成・配信の仕組みに統合されています。`seo/` と `sns/` を新設して同じ処理を複製する必要はありません。CSV記事とニュース記事を入口で分け、本文・SNS文面・配信結果を一緒に管理します。

1は顧客の非公開ファイルと納品物、3は営業先と連絡状態、4・7は公開情報と投稿履歴を扱います。依存ライブラリ、保管データ、実行場所が違うため、この境界では分割を維持します。特に公開記事の定期実行環境へ顧客の請求書を混ぜない構成にします。

Gemini呼び出しは似ていますが小さい部品です。今すぐ共有ライブラリ用の4つ目のリポジトリを作ると、それぞれの導入と更新が難しくなります。まず各ツールを単独で動かせる状態にします。FirecrawlやAIブラウザ、OpenHandsは必要な時だけ導入します。

## 実際につなぐ順番

最初の商品は、既存サンプルで実証できる「複数店舗の売上CSV → 明細と店舗別集計のExcel」を推奨します。複雑な請求書より入力と期待結果を決めやすく、APIキーなしでも動作を見せられます。

1. `office-worker` の `recipes/merge_sales.yaml` で完成見本を作る。顧客の列名、重複の扱い、締日、入力文字コード、検収条件を `jobs/<案件>/spec.md` に決める。
2. `outreach/config.yaml` の `offer` をその商品に揃える。実際に確認できた機能と納期だけを提案し、最初は少数の候補への文面と連絡先を人間が確認する。
3. 受注したら `python -m officeworker new 案件名`。営業先の情報を全部移すのでなく、合意した仕様と許可されたサンプルだけを案件へ渡す。
4. `content-engine/prompts/` を使い、同じ問題の解説記事とSNS下書きを作る。相談先URLを案内し、実際に試した結果と出典を添える。
5. 納品後、再販権を確認し、顧客名・金額・口座・固有の業務ルールを取り除いた別テンプレを作る。

今の3リポジトリ間に「受注 → 案件作成 → 請求」の自動連携はありません。上記は運用のつなぎ方です。次の実装候補は、共通の案件番号と受け渡し用の小さなJSONです。受注フローが固まってから、必要な項目だけで追加します。

## まだ出来上がっていない事業機能

- テンプレ販売ページ、決済、購入者への自動配布、ライセンス管理は未実装。
- 営業返信の取り込み、配信停止台帳、契約・請求・売上管理は未実装。
- スキャンPDFの文字認識は未実装。請求書の抽出精度は書式ごとの検収が必要。
- 記事の検索順位、広告審査、紹介報酬、フォロワー増加を保証する処理はありません。
- 大量生成・放置・30分納品での利益は保証しません。少数を確認し、納品品質と問い合わせ・成約の実績で次の投資を決めます。
